SECTION A

Blockers in the code

Every item here either gets the upload rejected outright or fails policy review. Five are done and verified against a real release build; PF-04 is the only one still open, and it is waiting on a product decision rather than on engineering time.

PF-01

Release builds are signed with the debug keystore

Fixed

android/app/build.gradle.kts sets signingConfig = signingConfigs.getByName("debug") inside the release block — the comment says it is there so flutter run --release works. Play refuses any artifact signed with the debug key, so nothing can be uploaded until this changes.

Done

Release signing now reads an untracked android/key.properties. When the file is absent the build still falls back to debug signing so a fresh clone can run flutter run --release, but it logs a warning saying the artifact cannot be uploaded. Keystores and key.properties are gitignored; key.properties.example carries the keytool invocation.

Still needs a human: generating the actual keystore and choosing its passwords. That key must be backed up somewhere the whole team can reach.

PF-02

The login screen lets anyone repoint the app at any server

Fixed

lib/main.dart had a _serverUrlController whose value was written to the base_url preference and used for every subsequent call, including /api/auth/login. That preference was read in seven files, each falling back to a separately hardcoded production URL.

Correction to the original assessment: this was first written up as an active credential-exfiltration path. On closer reading it was not — the controller was never bound to a TextField, so no shipped screen could set it, and _showServerConfig was assigned but never read. The real problem was a stored preference that release builds honoured without question, plus dead code that looked alarming. Worth fixing, but it was defence in depth rather than an open door.

Done

The base URL is centralised in lib/config.dart, and release builds now resolve to production unconditionally, ignoring any stored override. The dead controller, the unread _showServerConfig flag, and the error message pointing at a non-existent settings screen are all gone.

PF-03

usesCleartextTraffic="true" in the manifest

Fixed

AndroidManifest.xml opts the whole app back into unencrypted HTTP. The default base URL is already HTTPS, so nothing needs it — it is almost certainly a leftover from local development against a plain-HTTP dev server.

Done

Removed from the release manifest, and verified absent from the merged manifest of an actual release build. A debug-only network security config keeps plain HTTP working against a local API server, so nobody's dev loop breaks.

PF-04

No account or data deletion route exists

Only blocker left

Searching app/lib, backend/src and frontend/src for any deletion path returns nothing. Play's User Data policy requires apps with accounts to offer deletion both inside the app and at a publicly reachable web URL that can be used without installing the app.

There is a real nuance worth raising with whoever owns compliance: accounts here are provisioned by the school, not self-registered, and a parent deleting their own record has consequences for the school's attendance and fee history. The usual resolution for school-provisioned software is a documented request-and-erase route rather than a self-service hard delete — but the public URL and the in-app entry point are still required, and the Data Safety form asks for the URL directly.

Fix

Decide the deletion model first, then build: a settings entry in the app, a /delete-account page on the marketing site, and a backend route that performs whatever the decision turns out to be.

PF-05

REQUEST_IGNORE_BATTERY_OPTIMIZATIONS is declared

Fixed

Play treats this as a restricted permission with a narrow list of acceptable uses, and apps that declare it without qualifying get rejected. WorkManager background sync is not on that list on its own.

The permission turned out to be wired to two real Kotlin handlers on a method channel named /battery — but neither is ever invoked from Dart. The channel's only live method is saveFileToDownloads, which saves generated PDFs. The permission and both handlers were dead weight.

Done

Permission removed, along with the two dead Kotlin handlers and their imports. Verified absent from the merged release manifest.

PF-06

No build pipeline, and google-services.json is untracked

Fixed

.github/workflows/ contains only the three web deploy workflows. The Firebase config is correctly gitignored, which means any automated build needs it injected as a secret — and today the release bundle can only be produced on a laptop that happens to have both that file and the (not yet existing) keystore.

Done

.github/workflows/build-android.yml added: manual dispatch taking a version code, keystore and google-services.json injected from base64 secrets, flutter build appbundle, and an explicit check that fails the run if the result came out debug-signed. Signing material is deleted from the runner afterwards.

Still needs a human: the four repository secrets (ANDROID_KEYSTORE_B64, ANDROID_KEYSTORE_PASSWORD, ANDROID_KEY_ALIAS, ANDROID_KEY_PASSWORD) plus ANDROID_GOOGLE_SERVICES_JSON_B64. The workflow has never been run.

SECTION B

Decisions only you can make

These change the plan's shape rather than its contents. The first one changes the timeline by weeks, so it is worth settling before anything else starts.

1. Organization account, or personal?

This is the single biggest lever on the release date. Google requires new personal developer accounts to run a closed test with at least 12 testers for 14 continuous days before production access is unlocked. Organization accounts are exempt from that requirement.

Organization — recommended

Needs a verifiable legal entity and a D-U-N-S number. Verification takes days to a few weeks, but skips the 12-tester gate entirely and is the right fit for software sold to schools.

Personal

Faster to open, but adds a mandatory 14-day closed test with 12 real testers before you can ship to production — likely the longest single item on the critical path.

2. Does the app target children?

The audience declaration is not a formality. If the listing says the app is aimed at children, the Families policy applies: restricted SDKs, a stricter ads and data regime, and an additional review pass. Firebase Messaging in particular needs checking against that policy.

The likely correct answer is that the app targets parents, teachers and school staff — adults acting on behalf of students — which keeps it out of Families. That claim needs to be true of the UI, though: any student-facing surface makes it harder to defend.

3. App name and listing identity

The manifest label is ShikshaPilot (one word) while the product is branded Shiksha Pilot everywhere else. Pick one before the listing is created — the store name is changeable later, but the installed launcher label being different from the store name looks like an error to users.

4. Who is the account holder?

The Play account owns the app forever and is painful to transfer. It should belong to the company, on a shared address nobody loses access to — not an individual's personal Google account.

SECTION C

Console and listing work

Human work in the Play Console, most of it parallelisable with Section A. The privacy policy requirement is already satisfied.

PF-07

Data Safety declaration

Needs drafting

Must be accurate and match observable behaviour; mismatches are a common rejection cause. From the code, the app collects at minimum: phone number and password (login), name and role, student photos shown in profile and ID card screens, and an FCM registration token tied to the device. Each needs a purpose, a retention answer, and an encryption-in-transit answer.

PF-08

Store listing assets

Needs producing

A 512×512 icon, a 1024×500 feature graphic, between two and eight phone screenshots, a short description capped at 80 characters, and a full description. The screenshots are the real work — they need a populated demo school rather than empty states.

Blocked on B2

The IARC rating questionnaire and the target-audience declaration both flow from decision 2 above. Straightforward once that is settled.

SECTION D

Order of work

Numbered because the dependencies are real: account verification has the longest lead time and gates the last two phases, so it starts on day one regardless of code readiness.

01

Open and verify the Play account

Start immediately · days to weeks, mostly waiting

Settle decisions 1 and 4, pay the one-time $25 registration fee, and submit organization verification. Nothing else on this list takes as long in wall-clock time, and none of it is engineering effort.

02

Clear the code blockers

Parallel with 01 · PF-01 through PF-06

Signing config first, since nothing can be built or tested without it. PF-04 is the long pole — it needs a product decision before any code gets written, so raise it at the start of this phase rather than the end.

03

First signed bundle to the internal track

After 01 and 02 · same day once both land

Upload an .aab to the internal testing track, which has no review delay and takes up to 100 testers. This is where signing problems, missing ProGuard rules and release-only crashes surface — run it against the real production API before polishing any listing copy.

04

Complete the listing and policy forms

Parallel with 03 · PF-07 through PF-09

Data Safety, content rating, audience declaration, store assets, and the privacy policy and account-deletion URLs. Play will not let you promote to production with any of these outstanding.

05

Closed test with a pilot school

Optional for organizations · mandatory 14 days if personal

Worth doing on its own merits even when not required: one real school's parents and teachers on the closed track will find things no internal tester will. If decision 1 went the personal route, this phase is compulsory and needs 12 testers for 14 continuous days.

06

Production rollout

First review typically several days

Promote to production as a staged rollout rather than 100% — start around 20% so a release-only defect can be halted. Expect the first review to be the slowest; later updates clear much faster. Once live, swap the placeholder Play button on the marketing site for the real listing URL.
